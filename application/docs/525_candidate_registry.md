# R154 candidate registry and future collector wiring

This module validates append-only candidate evidence. It runs no model,
changes no old terminal/certificate, schedules no task and performs no network
or service operation. Only the exact NO3 larger-tau return followed by the AT
median return is eligible. NO3 failure blocks AT; the other five failed targets
are outside this pilot scope.

`validate_candidate_packet` binds the immutable original seven-target manifest,
exact target/seed/dimensions, honest project-consumer source, original units and
prior, zero-optimizer real bridge, full-state/RHS proof, completed-sweep index,
runtime, admission and whole-child ledger. It requires the original failed
artifact pins and a separate new attempt with max_iter300. Historical iterations
are paid and retained; no exact-resume, cap600 or refund label is accepted.

The bridge must bind full_state.rds and X/y references. Their sibling design
terminal must match the original target's seal and both byte hashes. Every
completed sweep has an immutable state pin and a declared complete factor and
schedule payload. The candidate contains compact beta_mean.bin/beta_cov.bin
with exact p-dependent sizes, vb_trace.csv and final_state.rds. The registry
hashes bytes but does not deserialize RDS or recompute numerical models.

Finalization has two phases: R exclusively writes terminal_core.json without a
future ledger pin. After the child is reaped, `finalize_terminal_core` creates
terminal.json by adding only the actual ledger_pin. Validation requires every
other parsed field to match the immutable core exactly. Both files are sealed;
the finalizer cannot alter acceptance, raw formal output, gates or source.

Before creating terminal.json, and again during packet validation, the ledger
must prove returncode0, reaped/drained execution, complete CPU accounting and
the private preexec/mandatory no-subprocess kernel boundary. A hashed
owned_guard_receipt_pin must independently have schema
r154_owned_stage_guard_receipt_v1, status EXITED, returncode0 and the same true
proof flags. Receipt source, target and exact child CPU must match the ledger;
when the ledger binds root_grant_sha256 the receipt must bind that same grant.
A stopped/reaped-but-aborted child cannot be finalized, even if terminal_core
was written before a later resource failure. Missing, changed or foreign guard
receipts reject before the final terminal is created.

Ledger validation also opens its pinned funding authority. Whole-stage actual
CPU must equal child CPU plus cumulative controller/helper CPU; administrative
CPU plus the reserved finalization tail must fit the parent reserve. The debit
must be max(actual, child plus full parent reserve). After candidate sealing,
registration requires the exact candidate-root finalization_accounting.json
with successful status, same source/target, paid final administrative CPU and
the same conservative whole-stage debit. Its immutable pin is stored in the
registration and rechecked on every later registration validation. Packet
validation remains possible before that final accounting file exists, so the
controller can finalize and seal before measuring its finalization cost. An
overrun cannot proceed to registration or branch admission.

All seven original independent measures and limits are present even when raw
formal convergence passes. Acceptance is exactly finite AND(formal OR
independent). Explicit computed nonfinite/NA values fail the independent branch;
they do not silently turn the OR into an AND. The producer must fail explicitly
if certificate evaluation throws before all seven values exist. A declaration
of completed evaluation is not a substitute for the producer's reviewed source.

`seal_candidate_packet` and `register_candidate` exclusively create new JSON
files. Even an accepted registration has status
`CANDIDATE_ONLY_NO_DEPENDANT_RELEASE`. A default `resolve_effective_task` call
returns the original packet. Only a separate exact root approval pin can select
the accepted sealed candidate for a future controlled consumer. No generic
truthy repair flag, path presence, synthetic result or stale source activates it.
Approval pins must come from the root control plane; these validators do not
authenticate the author of arbitrary user-created JSON.

The prepared full-regional route recognizes source class
`R154_project_fullstate_pilot_region`; it cannot masquerade as historical R141
or R146. It requires a separately approved full task inventory, all original
regional failures explicitly resolved, sealed payloads, unchanged exposure
labels, and twelve rows covering three folds and four operators. All four
score columns must be finite and nonnegative. Accepted metadata must be locally
available or explicitly materialized as a sealed snapshot; there is no implicit
remote-path fiction.

The current two-pilot scope cannot close NO3 while its smaller-tau failure
remains, or AT while its other three failures remain. Even a complete CSV or
a new truthy original seal cannot bypass that fact. A later expansion needs a
new explicit source/allowlist review. This module changes no active collector,
loader, controller, promotion or regional completion count.

Tests use a closed synthetic seven-target metadata fixture and tiny byte files;
only the manifest loader is substituted. Validators, hashes, OR logic, branch
gates and resolution/collector checks execute normally. No real target arrays,
RDS factors, fit, certificate recomputation or optimizer is loaded.
