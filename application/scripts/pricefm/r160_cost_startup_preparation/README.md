# Future cost startup repair: offline preparation

This packet prepares metadata startup code and private tests. It creates no
replacement decision, funding scope, claim, grant, scheduler job, or scientific
attempt. The original qualified 17 files and frozen FI/DK2 helpers are unchanged.
Current FI/DK2 keys, their old scopes, job 869420, and control scope03 are rejected.

The observed job 869420 worker stopped while waiting for activation, before its
payload. Separately, the actual stock `run_benchmark` AST prefix proves that a
stock cost authority lacking `role` raises `KeyError('role')` at its unconditional
execution-identity construction. That static failure was not reached by the
observed job. The killed controller's final usage is UNKNOWN; exit 137 alone does
not prove a CPU-limit cause.

`role_complete_authority_factory` copies stock `issue_authority` into private
globals. Its only authority-body changes are the exact FI/DK2 benchmark role,
root ticket/factory provenance fields, and `min(180, original_queue)` before
validation and sealing. It preserves original request validation, source/runtime
identity, resources, absolute expiry, transitions, transfer and proof checks.
The original authority and failed history are never edited.

`authorized_admission_bridge` copies the stock observer and overrides exactly
`canonical_claims` and `select_node` in the copy's globals. It requires the exact
AUTHORIZED operational/cost pair and matching authority SHA; the actual job
must be PENDING/JobHeldUser on the sealed node, one CPU and the exact 4 GiB request.
Stock physical sizing runs with no allocation added back. All source, original
calendar, handoff and cross-host overlap checks remain in the observer. The
mandatory authoritative replacement protocol supplies the complete readonly
cost-attempt view; this helper does not rewrite or ignore stock spent-region
history.

## Mandatory future protocol boundary

A funding file alone cannot admit another attempt. Stock reservation,
spent-region handling, overlap, initial-role restrictions, cost transitions and
collection routing currently reject replacements. A separate, explicit finite
root decision and authoritative replacement protocol must implement and review
all five routes, retain old paid 1200/230 reservations, old spent-region history,
the real FI 8.502209/8 overrun, and the unknown dead-controller usage.

The kit starts only from a future HELD replacement pair. Its ticket must bind
the new key/scope/job, exact release and qualified 17 sources, helper/bridge pins,
unchanged budgets, original finite expiry, replacement-decision pin and protocol
review pin. No such ticket is supplied here.

The required future protocol binding exposes `review_pin`, `module_pin`, the two
explicit metadata routing callbacks `_bound_claim`/`_cost_transition`,
`validate_binding(ticket,release)`, lightweight `read_authorized_pair`,
`current_claim`, `read_authority`, complete readonly `legacy_snapshot`, and its
reviewed admission view. The view must preserve all old history; it cannot
fabricate an unspent stock ledger. Shared qualified lifecycle parent markers and
all source/freshness checks must remain intact. This binding is intentionally
unimplemented; no default fallback, reserve call, replacement registry, or
automatic execution CLI exists in this packet. Low-level AST factories are
test/construction primitives, not independent execution authorization.

`validate_binding`, `read_authorized_pair` and `current_claim` must be bounded
metadata-only callbacks. They may not hide another full input hash, parent
reservation, observer, remote command or scientific action. `read_authority`
must verify the exact authority SHA and job/study/scope/resources/source identity.
The protocol's qualified lifecycle module must share the original parent marker
dictionary; the AUTH+observer and WATCH+ACTIVATE phases must close it only in
their combined finalizers. Those callback properties require independent review
of the eventual protocol module; this kit does not establish them for a module
that has not been written.

## Evidence and limits

Private tests exercise actual stock benchmark prefix statements before numerical
imports; role/queue AST changes; exact AUTHORIZED pair/job/resources; isolated
globals; future-only gates; wrapper call order; and unchanged budget arithmetic.
Earlier failed fixture/assertion runs are retained beside the passing run.

Root separately authorized `opaque_hash_feasibility.py`: two actual stock
`verify_release` calls read 1658 existing DK2 members /624095251 bytes as opaque
streams, without deserialization, numerical imports, canonical I/O or SSH. It
used 5.444500 SELF+children CPU seconds under an 8-second process cap, 5.322295 wall.
This filesystem state does not guarantee a future 8-CPU lifetime, scheduler/network
timing or the 30-second worker activation window. During any separately admitted
future startup, root should serialize its own CPU31 metadata work; this is not
permission to alter baseline or peer processes.

The future status driver must cap itself at **two** stock status calls: first
after 305 seconds, then, only if still active, at
`max(first_checked_epoch+301, allocation_start_epoch+1265)`. If that second
receipt is not terminal, stop without an implicit third call. A separately
reviewed cached metadata binder would be required for a different polling plan.
Each stock status call performs a full release check; four such calls would
exceed the observed 8-CPU hash budget. The original 20-metadata reservation remains
conservative and unused reservation is not refunded. Two full checks took 5.44
CPU seconds in the authorized fixture, which is partial feasibility evidence,
not a guarantee about every future cold lifecycle or scheduling condition.
